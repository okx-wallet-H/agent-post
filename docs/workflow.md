# 工作流：任务怎么分、怎么验收、怎么留痕

> 这是**流程本身**，也是这个仓库最值钱的部分之一：**每一步都留在 GitHub 上，可回溯、可复用。**

## 一、一条任务的生命周期（六步）

1. **立 Issue**（在本仓库）
   - 标题写"要什么"；正文必须有 **「怎么算做完（跑给我看）」** 勾选清单
   - 打标签：`type:task` + `area:*`（server / site / ops / docs）+ `P1~P4` + `agent:<执行者>`
   - 挂到对应 Milestone
2. **派活**（记录写进 Issue 评论）
   - 谁执行：服务器上的岗位机 Agent（Agent-A 等）或本机（温暖）
   - 机制：异步派活（任务文本写成文件 → `warm-dispatch <Agent> <taskfile>`，2~3 秒返回，不等）
   - 评论模板：`派出 2026-09-29 21:17 · 执行者 Agent-A · 任务原文见 docs/dispatch/2026-09-29-P1.md · 回收入口 <日志路径>`
3. **干活**（执行者自己拉代码/写文件）
   - 执行者**不改别人的文件**；一人一个交付物，接口由 Issue 写死
4. **回收**（证据进 Issue 评论）
   - 执行者把自己的自测输出贴回来；**没有输出 = 没干完**
5. **验收**（由温暖跑，不认"应该没问题"）
   - 在本地/临时环境**重跑一遍**执行者给的自测；再跑仓库自带 `server/smoke.sh`
   - 通过 → Issue 评论 `验收通过 + 我的实际输出` → 关 Issue
   - 不通过 → 评论具体失败点 + 回派（同一个 Issue，不新建）
6. **合并与留痕**
   - 合并进 `main`；`docs/devlog/<日期>.md` 记一笔：谁交了哪件、验收结果、卡点
   - CHANGELOG 只在**对外可见的版本变化**时更新

## 二、硬规矩（踩过坑总结的）
1. **"完成了"不算完成，"跑给我看"才算**（Issue 里必须有可执行验收）
2. **执行者不改公共文件**（`main.py` 只有集成者能改），避免两个 Agent 互相踩
3. **异步派活，不等**：派出去就继续干别的，靠 Issue 评论 + 枢纽事件回收
4. **一个 Issue 一个交付物**：混在一起无法验收
5. **不改别人机器上的东西**：执行者在自己的机器上写，产出物由集成者取回
