# 工作流（v2 · 2026-09-29 固化）

> 这套流程本身就是产品的一部分：**AgentPost 是用一个"人 + 一群 Agent"的团队做出来的**。
> 每一步都留在 GitHub 上：可回溯、可复用、可展示。

## 一、角色
| 角色 | 谁 | 干什么 |
|---|---|---|
| **产品/决策** | 人（H） | 定要什么、拍价格与边界、定要不要继续 |
| **集成与验收** | 温暖（本机 Agent） | 立 Issue、派活、**重跑验收**、合并、写 devlog |
| **执行者** | 岗位机 Agent（Agent-A/B/C、数据岗、暖暖机） | 一人一件交付物，在自己的机器上写，交自测输出 |
| **文案顾问** | 豆包（DoubaoWork） | 中文文案/口号润色、第二意见 |

## 二、一条任务的六步

1. **立 Issue**：标题写"要什么"；正文必须有 **「怎么算做完（跑给我看）」** 勾选清单；打标签 `type:task` + `area:*` + `P1~P4` + `agent:<执行者>`；挂 Milestone。
2. **派活**（异步，2~3 秒返回，不干等）：任务文本写成文件 → `warm-dispatch <Agent> <taskfile>`；同时在 Issue 里留一条**派出记录**评论（执行者、机器、机制、任务原文位置）。
3. **干活**：执行者按 Issue 的接口写自己的文件，**不许改别人的文件/公共文件**（`main.py` 只有集成者能动）。
4. **回收**：执行者把**自测输出**贴回来，报到事件流；没有输出 = 没干完。
5. **验收**（集成者执行，**不认"应该没问题"**）：取回交付物 → **重跑执行者给的自测** → 再跑仓库自带 `smoke*.sh` → 通过才写"验收证据"评论并关 Issue；不通过就贴失败点、同 Issue 重派。
6. **合并与留痕**：合并进 `main` → `docs/devlog/<日期>.md` 记一笔（谁交了哪件、验收结果、卡点）→ CHANGELOG 只在**对外可见版本变化**时更新。

## 三、硬规矩（每条都踩过坑）
1. **"完成了"不算完成，"跑给我看"才算**
2. **一人一个交付物**，接口在 Issue 里写死；混在一起无法验收
3. **执行者不许改公共文件**（避免互相踩）
4. **卡点必须报**：拉不到代码、缺凭据、跑不起来 → 立刻报，不许硬试、不许假装干完
   （实例：2026-09-29 我给错仓库地址，Agent-A/B 直接报卡点，避免了白干）
5. **派活的人不留着等**：派完继续干别的，靠 Issue 评论 + 事件流回收
6. **每次合并都留一句 commit 说明 + Issue 引用**（`feat(server): … (#3)`）

## 四、模板
- 任务 Issue 模板：`.github/ISSUE_TEMPLATE/task.md`
- 派活评论模板：
  ```
  **派出记录**（YYYY-MM-DD HH:MM）
  - 执行者：`agent:X`（机器 IP）
  - 机制：异步派活 `warm-dispatch X /tmp/task.txt`
  - 任务原文：`docs/dispatch/<日期>-P1.md`
  - 回收：执行者把自测输出报到事件流；集成者重跑后才算验收
  ```
- 验收评论模板：
  ```
  **验收证据**（集成者重跑）
  ```
  $ <执行者给的自测命令>
  <实际输出>
  ```
  已合并 commit <hash>
  ```

## 五、为什么这套值得展示
- **人是产品经理，Agent 是工程队**：一个人能干出一个团队的活
- **每一步有据可查**：Issue/评论/commit/devlog，天然是"开发直播"
- **卡点也是内容**：今天"我给错仓库地址 → 执行者报卡点 → 重派"这段，比任何宣传语都能说明这套协作是真的
